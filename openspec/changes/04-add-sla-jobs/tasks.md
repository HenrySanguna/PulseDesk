## Nota de arquitectura: sin `apps/worker` separado
El `proposal.md`/`design.md` de este cambio describen "un proceso (`api`) programa trabajos, otro proceso (`worker`) los ejecuta". Ese `apps/worker` NO existe en este repositorio — fue eliminado deliberadamente en `d1c07a9` ("fold worker process into api, move backend host to Render"), con una razón de infraestructura explícita y documentada: ningún hosting realmente gratuito soporta un segundo proceso siempre-activo (Fly.io perdió su tier gratuito), y `openspec/config.yaml` exige "restricción de coste cero". Esa decisión es anterior a este cambio (viene de `00-bootstrap-monorepo`) y sigue vigente — `libs/db/src/lib/valkey.provider.ts` y `libs/contracts/src/lib/env.ts` todavía tienen comentarios heredados mencionando `apps/worker` que ya no aplican.

Este cambio respeta esa decisión: los tres productores BullMQ (`SlaQueueService`, `AssignmentQueueService`, `MaintenanceQueueService`) y los tres consumidores (`SlaConsumer`, `AssignmentConsumer`, `SlaSweepConsumer`) viven dentro de `apps/api`, en `apps/api/src/sla/`, como módulo de Nest (`SlaModule`). La forma de sistema distribuido que describe `design.md` (programar vs. ejecutar, sobrevivir a la caída del otro lado) se mantiene igual — son clases separadas con conexiones a Valkey separadas — pero co-ubicadas en un solo proceso en vez de dos. El `sla:sweep` sigue siendo la red de seguridad real: si TODO el proceso `apps/api` se cae, al reiniciar recupera los vencimientos perdidos en su siguiente ciclo — el test 5.5 prueba exactamente ese escenario.

Se consideró (y se descartó) crear un nuevo `apps/worker` para este cambio: hacerlo revertiría una decisión de infraestructura ya tomada y documentada, sin que ningún task de este cambio lo pida explícitamente.

### Bug encontrado y corregido en la re-verificación (orquestador, no el apply anterior)
`SlaClockService.complete()` nunca volcaba el tiempo activo transcurrido a `consumedMinutes` (solo `pause()` lo hacía) — un reloj de `RESOLUTION` resuelto sin haber pasado nunca por `pause()` quedaba con `consumedMinutes` en 0 para siempre, así que `reactivate()` (al reabrir el ticket) recalculaba el tiempo restante como casi el presupuesto completo original, descartando en silencio el tiempo real ya consumido. Corregido: `complete()` ahora vuelca `businessMinutesBetween(activeSince, now)` a `consumedMinutes` antes de completar (mismo cálculo que ya hacía `pauseOne()`), salvo que el reloj ya esté pausado (su `consumedMinutes` ya lo refleja hasta `pausedAt`). Los dos tests de `tickets-sla-wiring.integration.spec.ts` que simulan "ya se consumieron X minutos" escribiendo `consumedMinutes` directo por Prisma ahora también resetean `activeSince: new Date()` en el mismo `update`, para no volverse dependientes del tiempo real de ejecución del test. Reverificado: 51/51 (`apps/api/src/sla` + `apps/api/src/tickets`) y 174/174 (suite completa) en verde tras el fix. Ver `verify-report.md` (Addendum) para el detalle completo.
