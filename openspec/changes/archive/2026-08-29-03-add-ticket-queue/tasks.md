## Nota de infraestructura (Batch 2)
Esta era la primera feature real de frontend del repo — `apps/agent-console` y `libs/ui` eran scaffolds vacíos de Nx. Se instalaron y fijaron las dependencias del stack no negociable de `openspec/project.md` que todavía no estaban en `package.json`: `primeng@22.0.0`, `@primeuix/themes@3.0.0` (reemplaza a `@primeng/themes`, deprecado por PrimeTek), `@angular/cdk@22.0.0` (peer de PrimeNG 22), `tailwindcss@^4.3.3`, `tailwindcss-primeui@^0.6.1`, `@ngrx/signals@^22.0.0` (mandado por project.md para estado de cliente — SignalStore, no señales sueltas). Todas fijadas a versiones cuyo rango peer de Angular coincide con el `@angular/core` ya instalado (`~22.0.4`); `primeng@^22.1.0` (la última) exige Angular `^22.1.0` y no se pudo usar. Se añadió `libs/ui/package.json` (antes no existía) y `apps/agent-console/package.json` (antes no existía) para que `@pulsedesk/ui`/`@pulsedesk/contracts` se resuelvan como paquetes reales de pnpm workspace en vez de imports rotos — el `apps/agent-console` original solo tenía un mapeo de tsconfig `paths` para `@pulsedesk/ui` que nunca llegó a probarse contra un consumidor real y fallaba con errores de `rootDir` de TypeScript. Se añadió un export `"./tickets"` a `libs/contracts/package.json` porque el barrel principal (`@pulsedesk/contracts`) re-exporta `env.ts`/`version.ts`, que usan `process`/`node:module` — código válido para Nest/Node pero que rompe la compilación de un bundle de navegador; `apps/agent-console` importa desde `@pulsedesk/contracts/tickets` en vez del barrel completo, sin tocar el barrel ni los imports existentes de `apps/api`/`apps/worker`. Se añadió `provideZonelessChangeDetection()` (faltaba en el `app.config.ts` generado, y sin él ni zone.js ni el scheduler zoneless quedan activos) y `proxy.conf.json` (proxya `/api` a `http://localhost:3000` en `nx serve agent-console`, para poder probar contra la API real en dev).

## Nota de verificación E2E (post-Batch 2)
Verificación manual en navegador real (Playwright) del flujo completo, hecha después de que Batch 2 reportara "listo" sin haber abierto la app en un navegador. Encontró y corrigió tres bugs reales que el build/lint/test en verde de Batch 2 no detectaba:

1. **`apps/agent-console/src/app/app.ts`/`app.html` nunca se conectaron al router** — seguían siendo el scaffold `NxWelcome` generado por Nx (`<pd-nx-welcome>` + `<router-outlet>` juntos, pero el welcome nunca se quitó). La app cargaba pero cualquier ruta (login, tickets) quedaba invisible detrás del scaffold de bienvenida. Corregido: `App` ahora solo renderiza `<router-outlet>`; `nx-welcome.ts` eliminado (ya no lo usa nadie).
2. **Falta login de agente** — no existía ninguna pantalla de auth en `apps/agent-console` (el login era backend-only desde `02-add-dual-auth`). Se agregó `apps/agent-console/src/app/features/auth/` (página de login, `AuthStore` con `@ngrx/signals`, `AuthApiService`) + `apps/agent-console/src/app/core/` (`authGuard` funcional protegiendo `/tickets`, `authInterceptor` funcional que redirige a `/login` en cualquier 401 salvo el propio intento de login). Contrato compartido nuevo en `libs/contracts/src/lib/auth.ts` (`@pulsedesk/contracts/auth`), mismo patrón que `tickets.ts`. Sesión solo en memoria (`AuthStore`) — no hay `GET /auth/me`, así que un reload duro pierde la sesión en el cliente aunque la cookie `pd_session` siga viva; el guard simplemente vuelve a pedir login (funciona, pero no persiste entre reloads — mejora de seguimiento, no bloqueante).
3. **`GET /tickets?page=N&pageSize=N` rechazaba valores válidos con 400** — bug real y previo en `apps/api`, no introducido en Batch 2. Causa: `apps/api/webpack.config.js` no externalizaba `class-transformer`/`class-validator` (mismo problema que ya se había resuelto para `argon2` en ese archivo: pnpm no hoistea dependencias de proyecto al `node_modules` raíz, y el auto-detector de externals de `NxAppWebpackPlugin` solo escanea la raíz). Webpack bundleaba dos copias físicas distintas del paquete — una para el import estático de cada DTO, otra para el `require()` dinámico interno de `ValidationPipe` (`@nestjs/common`) — y como el registro de metadata de decorators de `class-transformer` es un singleton por instancia de módulo, `@Type(() => Number)` quedaba registrado en una copia e invisible para la otra: el decorador nunca se ejecutaba, y `page`/`pageSize` llegaban como string a `@IsInt()`/`@Min()`, que los rechazaba. Corregido agregando ambos paquetes a `externals` en `webpack.config.js`, mismo patrón ya usado para `argon2`. Sin este fix, ninguna paginación real de la cola funcionaba — Batch 1 nunca lo detectó porque sus tests de integración llaman `TicketsService.listTickets(...)` directo, nunca `GET /tickets` por HTTP con query string real.

**Explorado y descartado** (no forma parte del fix): restaurar el mapeo de tsconfig `paths` para `@pulsedesk/ui` (documentado como quitado en la nota de infraestructura de arriba) rompe el build de nuevo ahora que `libs/ui` tiene componentes Angular reales cruzando el límite de `rootDir` — confirmado empíricamente, no es una opción viable tal como está la estructura del workspace hoy. Como consecuencia, **`pnpm nx serve agent-console` (dev-server Vite de Angular) no sirve la app correctamente en un navegador real** — falla al resolver `@pulsedesk/ui`/`@pulsedesk/contracts` de un modo distinto al de la build de producción (el dev-server de Vite sirve los chunks desde un directorio virtual `.angular/vite-root/` desconectado del `node_modules` real de `apps/agent-console`, que además pnpm no hoistea a la raíz). Probé también `prebundle.exclude` (opción real de `@angular/build:dev-server`) y falla por el mismo límite de `rootDir`. La verificación E2E de este documento se hizo sirviendo el build de producción (`nx build agent-console`) con un servidor estático + proxy `/api` ad-hoc, no con `nx serve`. Arreglar `nx serve` de verdad requiere reestructurar `libs/ui`/`libs/contracts` como libs "buildable" (con output compilado real, no TS crudo vía `exports` de package.json) o profundizar en la integración Vite/Nx/pnpm — no se intentó aquí por ser un cambio de arquitectura más grande, fuera de alcance de esta verificación puntual.
