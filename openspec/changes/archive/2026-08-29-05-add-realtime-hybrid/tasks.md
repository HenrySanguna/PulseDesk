## Nota de contrato: `TicketWithMessages.conversationId`
`ConversationStore` needs the REAL `conversationId` a widget socket auto-joins from its token — `ConversationGateway`'s rooms are keyed by that exact string, so an agent must `join` with the SAME id to ever see that conversation's traffic. Nothing exposed it before this change (`GET /tickets/:id` never included the reverse `Conversation` relation). Added `conversationId: string | null` to `TicketsService.getTicketForAgent`/`getTicketForCustomer`'s response (mirrored in `libs/contracts/src/lib/tickets.ts`'s `TicketWithMessages`) — a small, mechanical, low-risk addition (exposes already-computed data via one extra `include`), not a new business rule.

## Nota de arquitectura: sin `apps/worker` separado (bus de eventos)
Igual que `04-add-sla-jobs` (ver su propia "Nota de arquitectura", `openspec/changes/archive/2026-08-29-04-add-sla-jobs/tasks.md`), `proposal.md`/`design.md` de este cambio describen un "worker" (proceso separado) publicando eventos y una instancia `api` distinta reenviándolos a sus conexiones SSE. Ese `apps/worker` NO existe en este repositorio (`d1c07a9`, restricción de coste cero). Este cambio respeta esa decisión: `SlaClockService.breach()` (el código que en la topología descrita correría en el "worker") publica directamente en `RealtimeEventBusService` — el bus de Valkey en sí es real e íntegro (conexión de publicación y conexión de suscripción independientes, verificado en el test 5.3 contra Valkey real), lo que hace el diseño correcto para el día en que `apps/api` sí escale horizontalmente (explícitamente dentro-del-alcance-de-la-arquitectura-fuera-del-alcance-del-MVP según design.md), aunque hoy "worker" y "api" sean el mismo proceso.

## Nota de arquitectura: puente Conversation-Ticket
El `Conversation` model (`02-add-dual-auth`) y el dominio `Ticket`/`Message` (`03-add-ticket-queue`) nunca se conectaron antes de este cambio — `Conversation` no tenía relación alguna con `Ticket`, y `Message.ticketId` es obligatorio (no acepta `conversationId`). El contexto de este apply asumía que la reutilización de `Message.clientMessageId`/`@@unique([ticketId, clientMessageId])` para la idempotencia del widget (tareas 4.2/5.4) "ya estaba conectada" — no lo estaba; sin puente alguno, esas tareas eran estructuralmente imposibles de implementar, no ambiguas de producto.

Se cerró con el gap mínimo, mecánico, sin inventar una regla de negocio nueva: `Conversation.ticketId String? @unique` (migración `20260829160231_add_realtime_conversation_ticket_bridge`), creado perezosamente en el primer `message:send` del widget vía `WidgetMessagingService.getOrCreateTicketId` — reutiliza `TicketsService.createTicket` sin cambios (mismas reglas de SLA/prioridad que un ticket creado por un agente) y el mismo patrón de guarda atómica (`updateMany` con `WHERE ticketId: null`) que `TicketsService.claimTicket` ya usa para su propia condición de carrera. Se aceptó explícitamente el trade-off de que el perdedor de esa carrera (rarísima: dos pestañas del mismo widget enviando su primer mensaje en el mismo instante) deja un ticket huérfano ya creado (con SLA arrancado) en vez de añadir bloqueo/transacciones — ver el comentario de `getOrCreateTicketId` para el detalle completo.

## Nota de alcance: envío de mensajes por `ws` para agentes
El canal `ws` de chat es bidireccional en el transporte (agentes y widget comparten sala, reciben mensajes/typing/presencia en tiempo real por igual), pero el envío de mensajes AUTORADOS POR AGENTE sigue pasando por el endpoint REST ya existente y probado (`POST /tickets/:id/messages`, `03-add-ticket-queue`) en este batch — `ConversationGateway.handleMessageSend` solo acepta remitentes `widget` (`ONLY_WIDGET_CAN_SEND_HERE` para un socket de agente). Extender `message:send` a agentes es un follow-up natural, no ambiguo, pero no lo pide explícitamente ninguna tarea de este cambio ni la "Definición de terminado" (que solo exige la dirección widget -> consola en tiempo real). Como consecuencia, una respuesta de agente por REST no dispara un broadcast `ws` en vivo hacia el widget en este batch — documentado aquí en vez de dejarlo como un hueco silencioso.

### Descubrimiento durante la verificación: metadata de decoradores bajo SWC/vitest
El primer intento de `conversation-gateway.integration.spec.ts` (bootstrap completo de `RealtimeModule`/`AppModule` vía `Test.createTestingModule`) reveló que Nest no puede resolver parámetros de constructor tipados implícitamente (sin `@Inject()` explícito) bajo el pipeline de transformación de vitest/`@swc-node/register` — `Reflect.getMetadata('design:paramtypes', ...)` no captura correctamente el tipo cuando es una clase reexportada de otro paquete del workspace (`@pulsedesk/db`). Esto es preexistente en TODO el código de `apps/api` (nadie había hecho bootstrap real de Nest DI en un test antes de este cambio — cada test anterior construye servicios a mano con `new`), no algo introducido aquí, y el build de producción real (`webpack` + `compiler: 'tsc'`) no lo sufre. Corregido de forma mínima y no invasiva: se añadió `@Inject(Clase)` explícito SOLO a los archivos propios de `realtime/` y a `TicketsService`'s primer parámetro (`PrismaService`) — cambio seguro y retrocompatible con los 9 sitios de construcción manual existentes (`new TicketsService(...)`/`new SlaClockService(...)` en tests de `00`-`04`, todos siguen pasando sin cambios). El test final de la gateway usa un módulo de test mínimo y autocontenido (no `RealtimeModule`/`AppModule` completos) con dependencias inyectadas explícitamente, evitando así la necesidad de tocar `SlaModule`/`AuthModule`/`WidgetModule` (fuera del alcance de este cambio) para el mismo arreglo.

### Bug real encontrado y corregido durante la verificación (no solo un artefacto de test)
`ConversationGateway.handleConnection` es asíncrono (una sesión de agente necesita una ida y vuelta real a Valkey + Postgres), pero `NativeWsAdapter.bindMessageHandlers` conecta el listener `message` del socket de forma SÍNCRONA en cuanto el `Upgrade` termina, independientemente de si `handleConnection` ya resolvió. Un cliente rápido podía enviar `join`/`message:send` antes de que esa consulta a Postgres terminara, cayendo en un `authByClient.get(client)` todavía vacío. Corregido: `authByClient` ahora guarda `Promise<WsAuthContext | null>` (creada de forma síncrona, antes de cualquier `await`, como primera línea de `handleConnection`) en vez del valor ya resuelto — cada handler hace `await` sobre esa MISMA promesa, cerrando la carrera por completo. Confirmado por el propio test 5.5 (fallaba de forma intermitente antes del fix, en verde de forma consistente después).

### Bug CRITICAL encontrado en la re-verificación (orquestador) y corregido
`ConversationStore.join()` nunca mandaba `leave` de la conversación anterior antes de unirse a la nueva — el propio comentario de la clase decía "leave the old room, join the new one" pero el código no lo hacía. `ConversationRoomsService.join()` (servidor) es puramente aditivo, no reemplaza membresía, así que el socket del agente quedaba miembro de AMBAS salas al cambiar de ticket sin destruir el componente (la `RouteReuseStrategy` por defecto de Angular reusa `TicketDetail` entre cambios de `:id`). Consecuencia: presencia desactualizada, y mensajes/`typing` del ticket anterior filtrando al ticket actual (`handleMessage` no filtra por `conversationId`). Corregido: `join()` ahora manda `leave` de la conversación previa antes de unirse a la nueva, cuando el socket está realmente abierto. Reverificado: `pnpm nx run-many -t lint test build -p agent-console --skip-nx-cache` — verde (9/9 tests preexistentes, sin regresión). Ver `verify-report.md` (Addendum) para el detalle completo. Nota: no se agregó test dedicado para este fix — construir un harness real de `WebSocket` mockeado para los stores de tiempo real (`ConversationStore`/`DashboardStore`/`WidgetChatStore`) es trabajo real y no trivial sin patrón previo en este repo, ya señalado como WARNING de cobertura de tests en el verify-report; se trata como follow-up dedicado, no como un test aislado agregado solo para este método.
